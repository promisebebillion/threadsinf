# ThreadFlow

Текущий режим — **аккаунты Threads через браузерные сессии без настройки Meta API**. Пользователь входит сам в отдельном окне браузера; платформа сохраняет зашифрованную сессию в Supabase, проверяет выбранный профиль и использует её для текстовых публикаций. У каждого профиля отдельная сессия. Демо-аккаунтов и заполнения примерами нет. Проверка действительного входа и публикации именно в вашем профиле требует вашего завершённого входа.

## Запуск

Нужны Node.js 22.12+, npm и установленный Microsoft Edge или Google Chrome. На этом компьютере оба браузера доступны. Подключение к Supabase проекта `threadsinf` уже находится в локальном `apps/api/.env`.

```powershell
npm install
npm run dev
```

Открыть [http://localhost:5173](http://localhost:5173). API работает на порту 3000. Подготовка применяет миграции к Supabase; при неизменной схеме повторная генерация занятой Prisma DLL пропускается.

Только backend после подготовки:

```powershell
npm run dev -w @threadflow/api
```

## Подключить аккаунт

1. Войти в своё пространство ThreadFlow и открыть **Accounts**.
2. Нажать **Connect Threads account**, указать точный Threads **@username**, выбрать протокол прокси (SOCKS5 или HTTP / HTTPS), заполнить IP, порт, логин и пароль и нажать **Save & check proxy**. Затем открыть окно входа. На компьютере, где работает backend, откроется отдельное окно Threads через этот прокси.
3. Самостоятельно пройти вход на официальном сайте Threads/Instagram, включая подтверждение или двухфакторную проверку, если сайт их запросит.
4. Вернуться в ThreadFlow. Когда платформа определит именно выбранный профиль, подтвердить его имя и нажать **Save session**. Другой профиль, незавершённый вход или запрос SMS сохранить нельзя. Проверка восстановления выполняется в фоне; ручное окно остаётся открытым.
5. **Open Threads** открывает сохранённый профиль или использует его уже открытое окно. **Verify session** проверяет вход без новых видимых вкладок. Карточка показывает время последней проверки, запрос подтверждения, выход или невозможность проверки.
6. Для следующего профиля повторить подключение: окно начинает с отдельной чистой сессией, поэтому аккаунты не смешиваются.

Если сессия истекла или была отозвана, использовать **Reconnect** и войти заново. **Disconnect** удаляет сохранённые данные входа из подключения. Отмена незавершённого подключения закрывает его окно. Незавершённый вход ограничен 15 минутами.

Пароль Threads вводится только на официальном сайте. ThreadFlow не запрашивает его и не возвращает cookies в браузер платформы. Backend сохраняет cookies и необходимое состояние сайта зашифрованными AES-256-GCM в Supabase. До сохранения состояние проверяется в новом отдельном браузерном контексте: открывшаяся публичная страница профиля сама по себе не считается успешным входом.

Сохранение и повторное использование состояния основано на [документации Playwright](https://playwright.dev/docs/auth). Проверка собственного профиля сверена с [примером переключения аккаунтов Threads](https://github.com/Linx25059/Threads-account-switcher/blob/main/content.js); работа с браузерной формой публикации — с [исходниками Threads MCP](https://github.com/bintangtimurlangit/threads-mcp/blob/main/src/tools/write.ts). Эти примеры не заменяют проверку на действительном профиле.

## Возможности текущего шага

### Прокси аккаунта

На каждой карточке Accounts доступны поля **IPv4 address / Port / Proxy login / Proxy password**, проверка и удаление назначения. Пароль зашифрован AES-256-GCM в таблице `public.AccountProxy`; API его не возвращает. Пустое поле пароля при сохранении прежнего адреса и логина сохраняет существующий пароль. При смене адреса, порта или логина пароль нужно ввести заново.

Назначение сохраняется до первого входа: отменённая или неудачная попытка входа не освобождает прокси незаметно. Незавершённые назначения видны под аккаунтами и могут быть удалены. Уникальность **IP + порт** обеспечивается индексом Supabase в пределах пользователя, включая одновременные запросы. Другие логины для того же адреса и порта не обходят запрет. Это не гарантирует уникальность выходных IP у разных адресов провайдера.

Перед первым входом, восстановлением, открытием и публикацией скрытый запрос браузерного контекста определяет внешний IPv4 через HTTPS `api.ipify.org` и сравнивает его с прямым IPv4 backend (резервный сервис для прямого IP — Amazon). JSON-вкладка не создаётся. Затем в том же контексте загружается Threads: проверяются HTTP-ответ и появление элементов входа/интерфейса. Пустая оболочка с QR-кодом не считается успешной проверкой. При отказе прямого запасного соединения нет. HTTP использует CONNECT; SOCKS5 с паролем подключается через приватный локальный мост, поскольку Chromium не умеет такую SOCKS5-авторизацию. Мост принимает только HTTPS-туннели, требует случайные реквизиты, закрывается вместе с браузером и передаёт DNS-имя купленному прокси. Источники: [Playwright proxy](https://playwright.dev/docs/network#http-proxy), [SOCKS client](https://github.com/JoshGlazebrook/socks).

**Threads reachable** — результат проверки IP и загрузки интерфейса в указанное время, не подтверждение входа в аккаунт и не обещание постоянной доступности. Через пять минут карточка предлагает повторную проверку. Перед новым запуском проверка выполняется всегда; кнопку **Check proxy** можно нажать вручную. Если IP получен, но Threads не загрузился, сохраняется статус ошибки с найденными IP. Постоянных фоновых ping-запросов нет. Внешний IP backend может быть IP его VPN.

При конфликте SOCKS5 с VPN-туннелем можно задать `PROXY_NETWORK_INTERFACE` в `apps/api/.env`: точное имя физического адаптера Windows, например `Беспроводная сеть`. При каждом запуске определяется его текущий IPv4; только соединение до купленного прокси привязывается к этому адаптеру. VPN и системные маршруты не меняются. Если адаптер отключён, операция останавливается. Пустое значение использует системный маршрут. Такая привязка не исправляет фильтрацию сайтов или обрывы на стороне сети/прокси.

Чтобы изменить или удалить назначение, сначала закрыть окна Threads этого аккаунта и дождаться окончания публикации/проверки. Блокировка живых окон рассчитана на один экземпляр desktop-backend; горизонтальный запуск нескольких API для одного пространства не поддерживается. Если прокси не назначен, браузерные операции блокируются; сохранённые сессии и история остаются.

Реализованы подключение нужного профиля, проверка входа, сохранение, повторное открытие, переподключение и отключение сессий. Черновики, немедленная отправка и расписание хранятся в Supabase.

Текстовая отправка использует форму нового поста Threads. Перед нажатием Post проверяются ID и username, точный текст и действительность сохранённого входа. После отправки система ждёт короткое фиксированное время для распространения записи, один раз открывает профиль и обновляет DOM: нужен новый пост с нужным автором, полным текстом, временем и ссылкой. Неопределённый результат получает статус «Нужно подтвердить» и блокирует автоматический повтор; серия перезагрузок страницы не выполняется. Три прежние публикации уже подтверждены в профиле и исправлены в Supabase. Расписание выполняется только пока backend работает; SMS и security checks пользователь проходит самостоятельно.

Окно входа открывается на компьютере backend. Эта версия рассчитана на локальный запуск Windows; она не передаёт окно удалённого сервера в браузер пользователя.

## Supabase

Единственная база — Supabase, схема **public**. В [Table Editor проекта threadsinf](https://supabase.com/dashboard/project/asglentznxfmjtnydijr/editor) видны User, Session, OAuthState, SocialAccount, Post и PostTarget. Таблицы перенесены из прежней схемы threadflow без копирования или удаления записей. Prisma обращается к Supabase из backend. Supabase внутри использует PostgreSQL; отдельную локальную базу или Docker устанавливать не нужно.

Строка подключения находится только в `apps/api/.env`. Для другой копии взять строку из **Supabase → Connect**:

```dotenv
DATABASE_URL=postgresql://postgres:YOUR_URL_ENCODED_PASSWORD@db.YOUR_PROJECT_REF.supabase.co:5432/postgres?schema=public&sslmode=require
```

На этом компьютере настроен официальный IPv4 **Session pooler** из того же диалога: прямой IPv6 endpoint не отвечал. Скрипты отвергают базы вне Supabase. [Инструкция подключения Supabase](https://supabase.com/docs/guides/database/connecting-to-postgres).

RLS включён; клиентские роли не читают данные приложения. Backend проверяет владельца каждого аккаунта, поста и попытки подключения. В SocialAccount добавлены время и результат проверки сессии. Cookies и пароли не возвращаются через API.

## Настройки

| Переменная API | Назначение |
| --- | --- |
| `DATABASE_URL` | Подключение к Supabase |
| `THREADS_PROVIDER` | `browser` для текущего способа подключения |
| `PORT` | Порт API, по умолчанию 3000 |
| `FRONTEND_URL` | Локально `http://localhost:5173` |
| `TOKEN_ENCRYPTION_KEY` | Ключ AES-256-GCM, создаётся при первом setup |
| `SESSION_COOKIE_SECURE` | `false` для локального HTTP |
| `SESSION_COOKIE_SAME_SITE` | Локально `lax` |
| `TRUST_PROXY_HOPS` | Локально 0 |

Frontend использует `VITE_API_URL=http://localhost:3000`. Рабочие `.env` исключены из Git. Ключ шифрования нужно сохранить вместе с резервной копией базы; без него старые сохранённые сессии не восстановить.

## Проверки

```powershell
npm run setup
npm run typecheck
npm run lint
npm test
npm run build

# При работающем API, без открытия Threads и без публикаций:
npm run verify:api

# Таблицы и изоляция Supabase:
node scripts/check-database.mjs --verify

# Проверить сохранённые сессии без публикаций:
npm run verify:sessions

# Прокси: сохранение, шифрование, дубликаты и изоляция в настоящем Supabase:
npx tsx scripts/verify-proxies.mts
```

HTTP-проверка создаёт только своих временных пользователей и удаляет их в конце. Фиктивные Threads-аккаунты в продукт не добавляются. Отчёт находится в `output/verification-api.json`; границы проверки описаны в `docs/verification.md`. Подтвердить сохранение и восстановление именно вашего Threads-профиля можно только после вашего настоящего входа.

apps/web/src/                    React-интерфейс
packages/shared/                 Публичные типы API
